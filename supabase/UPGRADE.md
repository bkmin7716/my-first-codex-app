# 선수 명단과 사용자 연결 정책 적용 순서

1. 기존 함수 정의와 DB 백업을 확보하고 앱 입력을 잠시 중단합니다.
2. `001-player-slots-precheck.sql`을 실행합니다. 읽기 전용이며 설치된 함수·데이터를 바꾸지 않습니다. 행 수(기준: 게임 8, 참가자 13, 감사 30)와 내용 지문, 기존 함수 권한·정의를 저장합니다. 후보 검증에서 FAIL이 나오면 먼저 원인을 확인합니다. 기록을 삭제하거나 자동 변환하지 않습니다.
3. 기존 Supabase 프로젝트에서는 `001-player-slots.sql` 전체를 실행합니다. `schema.sql`은 새 프로젝트 전용이며, 새 프로젝트도 생성 후 이 마이그레이션을 적용합니다. 기존 게임·회원·감사 기록을 갱신하지 않으며 nullable slot과 중복 없는 유니크 인덱스를 준비하고 네 함수를 교체합니다. CREATE OR REPLACE는 함수 소유자와 기존 권한을 유지합니다.
4. `001-player-slots-postcheck.sql`로 행 수·내용 지문·권한이 이전과 동일한지 확인합니다. 기존 인덱스를 재사용했는지 확인합니다.
5. SQL 검증 후 이번 프런트엔드를 배포합니다. 기존 클라이언트는 생성자 명단 정책과 호환되지 않으므로 SQL과 앱을 함께 전환합니다.

생성자는 선수 4명 이름과 후세인 초기 순위를 직접 등록합니다. 계정 표시 이름(p_name)은 round.players와 별개입니다. 생성자와 참가자 모두 슬롯을 직접 선택하며 생성/참여/선택은 round.players를 바꾸지 않습니다. 재접속 시 기존 사용자 ID의 슬롯을 유지합니다. 익명 로그인은 동일한 브라우저 세션에 의존하므로 Safari 사이트 데이터를 지우지 않습니다.

`golf_mutate` 작업:
- `name`, `{value: "계정 표시 이름"}`: 자신의 golf_members.name만 변경. 선수 이름에 영향 없음.
- `player_name`, `{player: 0, value: "선수 이름"}`: 생성자만 등록 선수 이름 변경. 점수·정산 인덱스 보존.
- `slot`, `{value: 0}`: 자신의 미연결 슬롯만 연결. 점유 슬롯·재연결 거부. 선수 이름 불변.
- `initial`, `{value: [0,1,2,3]}`: 생성자만 변경, 홀 잠금이 있으면 거부.
- score/near/lock/finalize/rate/paid/settled/cash는 기존 작업 구조 유지.

선수 선택 정책은 sharedSlots가 JSON boolean true인 게임에만 적용합니다. sharedSlots가 없거나 null인 기존 후세인 게임은 슬롯 선택 없이 기존 참가자 점수 입력·홀 잠금 방식을 유지합니다. 기존 슬롯을 재배정하지 않습니다. 기존 일반 게임(sharedSlots가 boolean true가 아닌 normal)은 생성자가 혼자 1~4명 점수·잠금을 관리합니다. 일반 공동 게임은 sharedSlots=true와 선수 4명을 사용합니다. 최종 확정 중 새 슬롯 연결과 이름 변경은 차단합니다. 기존 참가자의 재접속 및 기존 슬롯 조회는 계속 허용합니다. 공동 게임의 선수 이름은 앞뒤 공백 제거 기준으로 중복을 금지합니다. 기존 최종 확정·홀 잠금은 그대로 유지됩니다.

이번 작업은 운영 Supabase에 SQL을 실행하거나 GitHub에 push하지 않았습니다. PostgreSQL 검증은 PGlite이며 브라우저의 Auth/Realtime 전송은 테스트 어댑터입니다. 실제 운영 Auth/Realtime 검증은 배포 후 별도로 수행해야 합니다.
